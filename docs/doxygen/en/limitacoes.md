@page page-limitacoes Known limitations and surprising behaviors

# Known limitations

Limitations verified by reading the code and the build configuration of this tree.
None of them is fixed here: they are recorded as they are. Where a line number is
given, it was checked against this tree.

## The version you read depends on where you look

The version value is not consistent across the channels:

| Channel | Where it is read | Value |
|---|---|---|
| `LIBZUPT_VERSION_STRING` | `include/libzupt_version.h:29` | `"1.0.15"` |
| `ZUPT_VERSION_STRING` | `include/zupt.h:120` | `"2.1.5"` |
| Key format | `include/zupt.h:126, 134` | 1 and 4 |
| Key format (C++) | `include/zupt_cxx.h:52` | 2 |
| Envelope format (C++) | `include/zupt_cxx.h:64` | 3 |
| `README.md` | `README.md:10, 19` | `"2.0.0"` |

The first two channels have distinct origins. `CMakeLists.txt:2-4` reads
`include/libzupt_version.h`, extracts `major.minor.patch` from the line that
defines `LIBZUPT_VERSION_STRING` by regular expression and hands the result to
`project(libzupt VERSION ...)` (`CMakeLists.txt:5`); from that value come
`PROJECT_VERSION`, the `VERSION`/`SOVERSION` of the shared library
(`CMakeLists.txt:80-81`) and the version of `libzupt.pc`. There is no version
header generated by the build — the tree produces no `build/libzupt_version.h`,
and the install rule copies `include/libzupt_version.h` itself
(`CMakeLists.txt:141`). The extraction by regular expression imposes the format: the
macro must start the line and contain exactly three numbers separated by dots,
otherwise `PROJECT_VERSION` is not derived. `zupt.h:120` declares its own
string, independent of all of this.

There is no C function that returns the version. The only programmatic access is
`zupt::getVersion()` (`src/zupt_crypto.cpp:420`), which returns
`LIBZUPT_VERSION_STRING`. An application that needs to compare the linked version
with the compiled one does not have that channel in plain C, and the four format
numbers (1, 4, 2, 3) do not refer to the same entity.

## Only three headers are installed

The only `install(FILES ...)` rule that copies headers (`CMakeLists.txt:138-143`)
installs `include/zupt.hpp`, `include/zupt_cxx.h` and `include/libzupt_version.h`.
The exported targets point the consumer to that directory
(`$<INSTALL_INTERFACE:include>` in `CMakeLists.txt:62` and `:100`), and `libzupt.pc`
does the same with `Cflags: -I${includedir}`. Therefore:

- `include/zupt.h` — the complete C interface — **is not installed**;
- `include/zupt_mlkem.h`, `include/zupt_x25519.h`, `include/zupt_keccak.h` and
  `include/zupt_cpuid.h` — **are not installed**;
- the library objects contain all the symbols of those interfaces, but the
  consumer's preprocessor does not find the declarations.

What remains is an installation that is coherent only for the C++ API: `zupt.hpp` includes
`zupt_cxx.h` (`include/zupt.hpp:53`) and `zupt_cxx.h` depends only on `<stdint.h>` and
`<stddef.h>` (`include/zupt_cxx.h:35-36`), so none of the installed files
references `zupt.h`. To use the C API one must compile from the source
tree or copy `zupt.h` by hand.

## The AES-NI/AVX dispatch reads a symbol nobody defines

The dispatch at `src/zupt_crypto.c:433` chooses between the assembly path and the
portable one by reading `zupt_cpu.has_aesni && zupt_cpu.has_avx`, and that line only exists
under `-DZUPT_USE_JASMIN`. `zupt_cpu` is declared `extern` in
`include/zupt_cpuid.h:70` and `zupt_detect_cpu()` in `include/zupt_cpuid.h:56`;
no `src/*.c` defines either of them.

In the default build (`ZUPT_USE_JASMIN` off) the code that references them is not even
compiled, and everything links. With the macro on, the shared library is still
built — the linker accepts undefined symbols in a shared object —
but linking an executable that reaches that branch fails with an unresolved symbol.
It is a path that depends on the caller supplying the definition from outside, without the
library exposing how. `zupt_detect_cpu()`, moreover, is not called anywhere
in this tree: even whoever defined it would never have its result
consumed.

## `zupt_random_bytes()` terminates the process instead of reporting an error

`src/zupt_crypto.c:126` defines `zupt_random_bytes()`. When entropy gathering
fails, the function writes to `stderr` and calls `exit(1)`
(`src/zupt_crypto.c:137` and `:153`), because salt and nonce must not be
predictable. The side effect is that a library returns a terminal error: the
caller has no way to handle the situation, recover from it or choose another
entropy source. Where this matters, the alternative is to generate the random bytes
on one's own and call the variants that take salt and nonce as arguments.

## `zupt_decrypt_buffer()` has three failure causes and a single signal

`src/zupt_crypto.c:738` returns `NULL` at exactly three points:

1. `pkglen < ZUPT_NONCE_SIZE + ZUPT_HMAC_SIZE` (line 741);
2. the `malloc` of the plaintext failed (line 777);
3. authentication failed — mismatched MAC or nonce not bound to the block and to the
   header (lines 782 through 786).

The three causes produce the same observable result, and `*olen` is filled in
before the MAC is checked, so that an authentication `NULL` arrives with a
plausible length written to the pointer. There is no error code and no diagnostic
channel. `pkg` and `kr` are also not checked against null: the first
access is `pkg` itself, in the HMAC call (`src/zupt_crypto.c:748`), and the
first access to `kr` is `kr->mac_key`, on the same line — `pkg == NULL` with
`pkglen >= 48` is an access violation, not a handled error. Distinguishing "invalid
format" from "wrong key" from "out of memory" requires checking the digest and the
length before calling.

## Keccak: two paths without a guard, reachable only by mistake

The internal helpers have two states that they themselves do not reject. Neither of
the two is reachable through correct use of the public APIs — every call to
`keccak_init()` passes a positive and fixed rate —, but both are documented
because reusing the helpers exposes them.

- `keccak_absorb()` (`src/zupt_keccak.c`) computes the free space as
  `rate - pt`. With `rate == 0`, the space is 0, the copied block is 0 and each
  iteration of the loop only applies one permutation without advancing the index: the loop does
  not terminate.
- `keccak_finalize()` closes the padding with
  `memset(ctx->buf + ctx->pt + 1, 0, ctx->rate - ctx->pt - 1)`. The operands
  are unsigned integers, so with `pt == rate` the computed length
  wraps to a huge value and the `memset` writes far beyond `buf`.

Both are recorded as `@warning` on the functions themselves, in the form they
have today.

## The C++ API: an opaque envelope header and two methods without a body

The C++ interface (`include/zupt.hpp`, implemented in `src/zupt_crypto.cpp`) is
compatible with the C one, but has three peculiarities.

**The envelope header is an opaque blob.** The constants that define the
v2 envelope are private to `src/zupt_cxx.c`: `ZUPT_ENCRYPT_BLOCK_SIZE`
(4 MiB), `ENVELOPE_PREFIX` (12 — `"ZUP2"` plus the `u64le` of the plaintext length)
and `ENVELOPE_TAG` (32), in `src/zupt_cxx.c:242-247`; the 52 bytes of
overhead per block record appear as a literal in the size formula
(`src/zupt_cxx.c:362`). None of this is in `include/zupt.h`, so on the C side the
caller receives the envelope as `uint8_t*` with a size and has no way to
interpret the fields without copying the constants from another TU. The 1137 bytes of the
hybrid header have the same problem on the other side:
`Encryptor::getEncryptionHeaderSize()` (`include/zupt.hpp:546`) returns the
constant `HYBRID_ENC_HEADER_SIZE`, but no accessor exposes a field of the
contents.

**`Encryptor::initEncryptionHeader()` (`include/zupt.hpp:564`) and
`Decryptor::deriveKeys(const std::vector<uint8_t>&)` (`include/zupt.hpp:699`)
are declared and have no definition.** They do not appear in `src/zupt_crypto.cpp` nor
in `build/libzupt_static.a`. They are also not called by anything in this tree, which
explains why the library links: the link fails only if an external
caller goes through them. The same applies to the member
`Decryptor::encryptionHeader_` (`include/zupt.hpp:703`): no read or
write of it exists in `src/` — all the uses of `encryptionHeader_` that exist
are from the `Encryptor`.

**`zupt::secureWipe` is declared twice** in the same header, in
`include/zupt.hpp:229` and `include/zupt.hpp:742`, with an identical signature. It is
redundancy, not conflict.

## Limitations of the bindings

The bindings in `examples_*` are examples that became public surface: each one
has details that a consumer will find.

**Java (`examples_java/`).** `Encryptor.java` is the only class that uses a native
method without `System.loadLibrary("Jzupt")` — `KeyGenerator.java:14`,
`Decryptor.java:10`, `NativeLib.java:9` and `ExampleBasic.java:10` have the
static loading block. If the application uses only `Encryptor`, the library is never
loaded: `JNI_OnLoad` does not run, no method is registered and the call becomes an
`UnsatisfiedLinkError`. In addition,
`Java_com_libzupt_Encryptor_nativeEncryptMemorySecure`
(`examples_java/zupt_jni.cpp:894`) is implemented but is not in the
`encryptorMethods` table (`zupt_jni.cpp:413`) nor declared as `native` in
`Encryptor.java` — `encryptMemorySecure` delegates to `nativeEncryptMemory`
(`Encryptor.java:34`). By the same path,
`Java_com_libzupt_Decryptor_decryptMemorySecure` (`zupt_jni.cpp:1062`) is dead
code: the Java method of the same name (`Decryptor.java:39`) calls
`decryptMemoryNative` and only wraps the result in a `SecureBuffer`. The element
counts passed to `RegisterNatives` are hand-repeated literals
(`zupt_jni.cpp:523, 529, 535, 541`), not `NELEMS`. Finally, the file does not
implement `JNI_OnUnload`, so the global references created in
`JNI_OnLoad` are not released when the class is unloaded.

**Python (`examples_python/zupt_pybind.cpp`).** `zupt::ZuptError` is registered
with `py::register_exception` (`zupt_pybind.cpp:140`), which creates an exception
derived from `RuntimeError` with no methods: the error code of `ZuptError::code()`
is lost when crossing the boundary, leaving only the message. `secure_wipe(ptr,
size)` (`zupt_pybind.cpp:742`) is a direct forward to
`zupt::secureWipe(void*, size_t)` and receives an integer address coming from the
interpreter: `secure_wipe(0, 16)` is a null write, with no check whatsoever.

**Node.js (`examples_nodejs/src/zupt_napi.cpp`).** Numeric arguments are
converted with `Uint32Value()` (`zupt_napi.cpp:291` and `zupt_napi.cpp:853`), which
makes `randomBytes(-1)` become `4294967295` and the allocation try four gigabytes
instead of reporting an error. The `Encryptor` and `Decryptor` classes do not call
`IsBuffer()` at any point in the file: a `napi_value` that is not a `Buffer` reaches
the pointer conversion without verification.

## 52 symbols declared without definition

Checking what `include/` declares against what `build/libzupt_static.a`
actually contains (`nm --defined-only`), 52 names appear in the headers and in no
object of the library. They split into two very distinct groups.

**Jasmin and CPU (6 symbols)** — `zupt_aes256_blk`, `zupt_aes256_ctr4`,
`zupt_ct_select_32`, `zupt_fe_cswap`, `zupt_mac_verify_ct` (declared in
`include/zupt_jasmin.h`) and `zupt_detect_cpu` (`include/zupt_cpuid.h`). There is
no assembly file in this tree. The first five are called
only inside `ZUPT_USE_JASMIN` compile-time conditional blocks
(`src/zupt_crypto.c:427-475` and `:753`, `src/zupt_mlkem.c:1088` and
`src/zupt_x25519.c:252`); `zupt_detect_cpu` has no call site
outside its own declaration. It is the same case as the AES dispatch described
above: the macro turns the consumption on and there is nobody to supply the definition.

**Format, compression and deduplication (46 symbols)** — the whole set of
files, declared in `include/zupt.h`:

- container: `zupt_compress_files`, `zupt_compress_solid`,
  `zupt_extract_archive`, `zupt_list_archive`, `zupt_test_archive`;
- disk: `zupt_disk_backup`, `zupt_disk_restore`;
- codecs: `zupt_lz_compress`, `zupt_lz_decompress`, `zupt_lz_bound`,
  `zupt_lzh_compress`, `zupt_lzh_decompress`, `zupt_lzh_bound`,
  `zupt_predict_build`, `zupt_predict_encode`, `zupt_predict_decode`,
  `zupt_predict_benefit`, `zupt_resolve_auto_codec`, `zupt_codec_name`,
  `zupt_detect_filetype`;
- internal serialization: `zupt_w8`, `zupt_w16le`, `zupt_w64le`,
  `zupt_write_varint`, `zupt_read_varint`, `zupt_encode_varint`,
  `zupt_decode_varint`, `read_block`, `read_enc_header`,
  `write_enc_header`, `decompress_block`;
- deduplication: `zupt_dedup_init`, `zupt_dedup_free`, `zupt_dedup_lookup`,
  `zupt_dedup_insert`, `zupt_dedup_record_hit`, `zupt_dedup_record_block`,
  `zupt_dedup_stats`, `zupt_dedup_write_ref`;
- utility and discovery: `zupt_filelist_init`, `zupt_filelist_free`,
  `zupt_filelist_add`, `zupt_collect_files`, `zupt_default_options`,
  `zupt_format_size`, `zupt_strerror`.

The practical effect: the types (`zupt_archive_header_t`, `zupt_index_entry_t`,
`zupt_block_t`, `zupt_dedup_ctx_t`), the codec identifiers and the header flags
exist and describe a format — but nothing in this tree produces or
consumes that format. No call to those 46 names appears in `src/`, and they
do not appear in the bindings or in `tests/` either.

The error type of that half of the interface, `zupt_error_t` (`include/zupt.h:416`),
follows the same rule: apart from `include/zupt.h` itself, where it appears in 19
lines, it is not cited in any `src/`, `tests/` or `examples_*`. The
implementations that actually exist report failure through `NULL`, a C++ exception
(`zupt::ZuptError`) or `exit(1)`; the enumerated error code is left reserved for
functions that do not exist.

## The container flag bits are not read by anything

The eight `ZUPT_FLAG_*` defined in `include/zupt.h` (lines 210, 221, 229, 236,
245, 250, 257 and 1514) do not appear in any executable part of `src/`: if the
comments are disregarded in the search, the result is empty. This includes
`ZUPT_FLAG_DISK_IMAGE` (bit 6), which `@ref zupt_disk_backup` receives in `opts`
as if it controlled a behavior, and `ZUPT_FLAG_CKSUM_XXH64`, which expands to
`(0u << 5)` — turning it on turns on no bit.

Together with the previous section, the picture is coherent: the bits describe a
file format whose reading and writing are not implemented in this tree.

## Test coverage

The `ctest` of this tree runs 14 tests and the 14 pass. What they cover, however,
is the cryptographic core: `keygen`, `encrypt`, `decrypt`, `roundtrip`,
`file_ops`, `authentication`, `secure_buffer`, `key_storage` (UNIX only),
`fuzz_smoke`, plus four checks in Python (`acvp`, `primitives`,
`legacy`, `migration_cli`) and a test of the portable AES.

Two points of attention:

- `tests/fuzz_decrypt.cpp` does not appear in `tests/CMakeLists.txt`. The only target
  that compiles it is `zupt_fuzz_decrypt` (`CMakeLists.txt:204-212`), guarded by
  `LIBZUPT_BUILD_FUZZERS`, which is `OFF` by default and requires Clang. That target is not
  registered as a CTest case, so `ctest` runs only `fuzz_smoke`.
- No test reaches the files and disks API, which was expected: the
  functions do not exist. The `file_ops` tests exercise only
  `Encryptor::encryptFile`/`Decryptor::decryptFile` from the C++ layer;
  `zupt_read_file` and `zupt_write_file` are not called by any test, and the
  `.zupt` container is not read or written anywhere.
