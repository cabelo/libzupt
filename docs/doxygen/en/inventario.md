# How to read this inventory

Three numbers are measured per file, and they measure different things:

- **Blocks** — Doxygen comments written in the file. Counted by the start of
  the comment (`//!`, `///`, `/**` or `/*!`), once per block, regardless
  of how many lines it occupied.
- **Items** — entries that Doxygen placed in the API item list starting from
  the file: the file itself, the structures, unions, enumerations and classes
  declared in it, and the functions, variables, macros, typedefs, enumerators and
  members declared in it. Each item counts once, by its identifier.
- **Doc** — of the previous items, how many have text: a non-empty brief
  description or detailed description in the XML generated by Doxygen.

In every file of the table **Doc equals Items**. There is no item in the
API item list without text, which is checked by the `Doxyfile` options
`WARN_IF_UNDOCUMENTED = YES`, `WARN_IF_DOC_ERROR = YES` and `WARN_NO_PARAMDOC = YES`:
the generation produces no warning.

The number of blocks can differ from that of items for two reasons: a single
comment can describe several members (the fields of a structure or the
enumerators of an enumeration written with the suffix `/**< ... */`), and a
comment can describe something that the Doxygen 1.8.14 parser does not represent
as a list item. The two concrete cases are explained in
@ref inv-limites.

# Symbols declared without definition

The coverage above measures *documentation*, not *implementation*. Comparing
what `include/` declares with what `build/libzupt_static.a` contains
(`nm --defined-only`), **52 of the 113 names** appear in the headers and in no
object. They are documented — `@brief`, parameters and notes — and have no body.

The distribution:

| Group | Count | Where they are |
|---|---|---|
| Jasmin and CPU primitives | 6 | `include/zupt_jasmin.h`, `include/zupt_cpuid.h` |
| Files, codecs and deduplication | 46 | `include/zupt.h` |

The complete list is in @ref page-limitacoes, which also explains why the
link does not break today (the users of those names only exist under
specification condition macros that are off, or do not exist).

This does not affect the coverage check: Doxygen requires documentation for
everything that it *declares*, and those 52 symbols are documented like the
rest. But it means that the phrase "the entire API is documented" should not be
read as "the entire API exists".

# Where the numbers diverge and why

- `include/zupt.hpp` has 135 blocks for 79 items: the methods of the classes are
  declared and documented here, and only implemented in
  `src/zupt_crypto.cpp`. The definitions in that file do not generate new items
  because the documentation is already attached to the declarations. This is why
  `src/zupt_crypto.cpp` appears with a single item: the file itself.
- `src/zupt_keccak.c` (10 blocks, 22 items) and `src/zupt_cxx.c` (12, 19):
  section comments describe groups of internal functions, and fields of
  private structures are documented at the point of definition.
- `examples_python/zupt_pybind.cpp` has 47 blocks for 2 items: most of the
  documentation is on lambda expressions registered in
  `m.def(...)`. Doxygen 1.8.14 does not create a list item for a lambda, so the
  text appears on the file page and on the parameters described in a nominal
  list, but not on their own pages. The two items are the file and the module
  function.
- `include/zupt_jasmin.h` has 4 blocks for 1 item: three of the comments
  describe prototypes that only exist under the specification condition macro,
  which is not defined in the normal generation, so they do not become items.
- `include/zupt.h` has 167 blocks for 195 items because the fields of several
  public structures are documented in the block of the structure.
